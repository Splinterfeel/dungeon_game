# Unity-клиент: план первого играбельного прототипа

Дата: 2026-10-02. Статус: реализация начата; основа проекта и экран временного
выбора пилота собраны. Список, выбор и создание пилота проверены в открытом
Unity Editor с живым сервером. Дальнейшую работу над интерфейсом отложили до
более мощного компьютера.

Цель — пройти в настоящем Windows-клиенте всю петлю:
выбрать пилота → настроить два меха → создать/найти лобби → сыграть матч →
получить прогрессию и деталь → изменить сборку → сыграть следующий матч.
Серверные правила и PostgreSQL уже существуют. Клиент отображает данные
и отправляет намерения игрока; сервер проверяет действия и сохраняет результат.

Связанные документы: [ROADMAP.md](ROADMAP.md),
[PERSISTENCE.md](PERSISTENCE.md), [AGENTS.md](../AGENTS.md).
Плейтест с людьми пока отложен; техническая проверка нового клиента обязательна.

## 1. Основа и ограничения

- Unity 6 LTS, C#, URP, Windows x64. Точную установленную версию фиксируем
  в проекте и не обновляем посреди этапа без причины.
- Проект в `client/DungeonClient/` внутри этого репозитория: `Assets`,
  `Packages`, `ProjectSettings` и `.meta` храним в Git; `Library`, `Temp`,
  `Logs`, `Obj`, локальные сборки исключаем. Сериализация ресурсов — текстовая.
- Предлагаемый вид первой версии: небольшая 3D-арена с клетками,
  ортографическая камера под углом, простые составные мехи из примитивов.
  Камеру можно перемещать и приближать. Финальные модели и анимации позже.
- Экранный интерфейс — UI Toolkit с UXML/USS: списки пилотов/лобби,
  карточки деталей и HUD удобно задавать текстовыми ресурсами и редактировать
  в UI Builder. Метки над мехами сначала проецируем в экранный UI.
  Это выбор под наши списки и способ разработки, а не утверждение, что
  UI Toolkit всегда лучше uGUI. Используем одну UI-систему в первом клиенте.
- REST — `UnityWebRequest`; JSON — официальный Unity-пакет Newtonsoft Json.
  Он нужен для вложенных списков карты, словарей и nullable-полей контрактов.
  В C# — обычные типизированные DTO; Pydantic остаётся на Python-сервере.
- Для WebSocket сначала проверяем `System.Net.WebSockets.ClientWebSocket`
  в редакторе и Windows-сборке. Если установленная версия Unity имеет
  несовместимость, выбираем одну небольшую библиотеку после проверки.
  WebGL и другие платформы сейчас не расширяют требования к транспорту.
- Адрес сервера задаётся настройкой; локальный вариант —
  `http://127.0.0.1:8000`. URL WebSocket строим из того же адреса.
  Клиент не получает пароль PostgreSQL и не подключается к БД напрямую.
- Ноутбук i5-1035G / 8 ГБ RAM: один редактор, небольшие сцены, простые
  материалы, ограниченные тени, без тяжёлого постпроцессинга. Начальная цель
  для проверки — комфортные 30 FPS при 1280×720 в сборке; измеряем на ноутбуке.

Документация Unity: [сравнение UI-систем](https://docs.unity3d.com/6000.0/Documentation/Manual/UI-system-compare.html),
[Newtonsoft Json](https://docs.unity3d.com/Packages/com.unity.nuget.newtonsoft-json@3.2/manual/index.html).

### Unity CLI и Pipeline на этой машине

- Unity CLI установлен вместе с Hub: `C:\Program Files\Unity Hub\resources\unity.exe`.
  В обычном PowerShell пользователя он доступен как `unity`.
- Для команд к открытому Editor нужен пакет `com.unity.pipeline`; он добавлен
  в `client/DungeonClient/Packages/manifest.json`. Editor надо открыть после
  установки пакета, затем `unity status --json` должен показать `state: ready`.
- Pipeline обнаруживает Editor через
  `Library/Pipeline/.unity-pipeline-port`. Файл содержит bearer-токен и Unity
  намеренно закрывает его правами текущего пользователя. Процесс агента работает
  от `DESKTOP-B6NSVDO\CodexSandboxOffline`, поэтому без явного чтения файла
  он не может послать команду даже при открытом Editor.
- При явном согласии пользователя, пока Editor открыт, дать агенту только чтение
  этого файла: `icacls "C:\code\dungeon_game\client\DungeonClient\Library\Pipeline\.unity-pipeline-port" /grant "DESKTOP-B6NSVDO\CodexSandboxOffline:(R)"`.
  После перезапуска Editor файл создаётся заново, доступ выдаётся повторно.
  Не открывать доступ ко всему `Library` и не сохранять токен в Git/документации.
- Проверка соединения агента: `unity status --json`, затем
  `unity command --project-path "C:\code\dungeon_game\client\DungeonClient"`.
  Через Pipeline доступны создание сцен, проверка и запуск пользовательских
  C#-команд; это не заменяет визуальную проверку пользователя в Game View.
- `status` проверяет локальный HTTP-сервер Pipeline, но не гарантирует, что
  главный поток Editor выполняет команды. Если `editor_status` и операции со
  сценой завершаются по тайм-ауту, проверь состояние окна Editor и
  `client/DungeonClient/Logs/Editor.log`. Не запускай цепочку новых команд,
  пока главный поток не отвечает. Для работы при неактивном окне Pipeline
  предоставляет `set_autotick`; включай его после восстановления Editor.
- На этой машине запуск отдельного Editor через `Unity.exe -batchmode` упирался
  в `LicenseClient-user`; `-automated -nographics` не решил проблему.
  Установленный Pipeline в обычном открытом Editor позволяет агенту работать
  без второго процесса Editor.

## 2. Экраны и переходы

```text
Выбор пилота → Маршрут пилота → Гараж
                         ↓
                 Лобби: список / создание
                         ↓
                 Комната ожидания
                         ↓
                       Матч
                         ↓
                     Результат → Маршрут пилота
```

### Выбор пилота — временный логин

- Список сохранённых имён с уровнем; при совпадении имён добавляем короткий ID.
- Обновление списка, выбор и вход. Последнего пилота запоминаем локально,
  но проверяем, что он ещё существует на сервере.
- Кнопка «Новый пилот»: имя и случайные стартовые сборки. Профиль и две
  сборки создаются на сервере сразу, чтобы гараж был доступен до первого матча.
- После входа открывается экран маршрута с кнопками «Гараж» и «Лобби»;
  пока реализован только переход в гараж. Пустой список и недоступный сервер
  имеют отдельное понятное отображение.
- Это выбор тестового профиля по UUID, без пароля и подтверждения личности.

### Лобби — список, создание и комната ожидания

- Список: название, занятые места, режим «PvP / против бота», статус матча.
  Кнопки «Обновить», «Присоединиться», «Создать», «Гараж».
- Создание: название и галка «Против бота». Первый целевой формат фиксирован:
  два пилота, по два меха каждому; против бота — один человек команды 1.
  В PvP при присоединении выбираем свободную команду.
- Карта пока одна (`map_2`), нейтральных врагов два — так запускает сервер.
  Эти параметры показываем как информацию. Выбор карты, отключение PvE,
  таймер хода и прочие галки появляются только вместе с серверной поддержкой.
- Создатель после создания проходит обычное присоединение: создание лобби
  само по себе сейчас не добавляет пилота в участники.
- В комнате ожидания: участники по командам, имена, обозначение бота,
  хост и статус ожидания. Кнопка старта доступна хосту при полном составе;
  сервер также проверяет это. Отдельные ready-галки для первой версии не нужны.
- WebSocket открывается после присоединения, ещё до старта: все участники
  узнают о старте и автоматически переходят в матч.
- Выход до старта освобождает место. Если выходит хост, простое начальное
  правило — закрыть не начатое лобби и вернуть остальных в список.
- Список обновляется вручную и периодически, пока открыт, без перекрывающихся
  запросов. Внутри комнаты изменения приходят по WebSocket.
- Из комнаты гараж доступен для просмотра. Редактирование — до вступления
  в лобби или после выхода, чтобы сборка перед стартом не менялась незаметно.

### Матч

- Построить пол и стены из серверной сетки. Координаты сервера `(x, y)`
  переводить в Unity `(x, 0, y)` одним явным преобразованием.
- Показать два своих меха, видимых противников и нейтральных врагов.
  Цвет/контур различает команды; у каждого меха отдельный `actor_id`.
- Клик по меху открывает карточку; выбор для осмотра не меняет очередь хода.
  Управлять можно только текущим живым мехом выбранного пилота.
- HUD: раунд, фаза, чей ход, HP, AP, расход движения, оружие по рукам,
  прочность корпуса/головы/ног и каждой руки, навыки и overwatch.
- Клетки движения подсвечиваются из `turn.available_moves`. Выбор клетки
  отправляет `MOVE`; сервер определяет путь, стоимость и промежуточные шаги.
- Выбор оружия и видимой цели → подтверждение атаки → `ATTACK` с
  `params.weapon_id`. Уничтоженная рука делает её оружие недоступным.
  Атака союзника недоступна; ошибки дистанции/AP/преград объясняет сервер.
- Кнопки `OVERWATCH` с выбранным дальнобойным оружием и `END_TURN`.
  При чужом ходе, завершении матча или потере соединения команды выключены.
- Инспекция — локальная карточка уже полученных данных. `INSPECT` и
  `HEAVY_ATTACK` есть в enum, но обработчик их сейчас не реализует:
  не добавляем неработающие команды в UI.
- Журнал показывает `game_event.message`. Базовые эффекты движения и
  попаданий добавляем после рабочего управления; текст событий не парсим
  для вычисления урона, XP или определения завершения матча.
- Противник, исчезнувший из отфильтрованного состояния, скрывается, а не
  обязательно считается погибшим. Полную карту сервер отдаёт уже сейчас;
  маски видимости клеток в DTO нет. Настоящее затемнение невидимых клеток —
  отдельное улучшение контракта, не имитация скрытой информации на клиенте.
- Завершение определяем по `ended`/`winner`, результат показываем один раз:
  победа/поражение/ничья, XP, новый уровень и выпавшая деталь либо отсутствие
  дропа. Затем обновляем гараж с сервера.
- Выход из текущего матча означает отключение клиента, без начисления
  поражения за сдачу. Сдача и таймеры отсутствуют в текущих правилах;
  не делаем кнопку, обещающую их. Восстановление боя после падения сервера
  в этот план не входит.

### Гараж

Реализован и закрыт. Архитектурные решения, инварианты, схема данных и
контракт Unity с сервером зафиксированы в [GARAGE.md](GARAGE.md).

## 3. Что уже есть на сервере и что потребуется

| Возможность | Текущий контракт | Действие в плане |
| --- | --- | --- |
| Список пилотов | `GET /pilots` | Готово: временный выбор имён без debug-префикса |
| Создание пилота до лобби | `POST /pilots` | Готово: создаёт UUID, две стартовые сборки и возвращает гараж |
| Список/создание лобби | `GET /lobbies`, `POST /lobbies` | Использовать; клиент фиксирует два места |
| Присоединение | `POST /connect_lobby`, UUID + team | Использовать с существующим профилем |
| Состав комнаты | WS `lobby_state` | Готово: UUID для совместимости и структурированные участники с именем/командой/ботом |
| Выход из комнаты | `POST /leave_lobby` | Готово для не начатого лобби; уход хоста закрывает комнату и шлёт `lobby_closed` |
| Старт | `POST /start_game` с `host_player_id` | Готово: сервер проверяет хоста |
| Бой | WS `/ws/{lobby_id}/{player_id}` | Использовать тот же сокет, что в комнате |
| Результат команды | Адресный WS `action_result` | Готово: ID команды, `performed`, текст причины; работает и для отказов до боевого обработчика |
| Результат матча | Адресный WS `match_result` | Готово: ID матча, победитель, XP, уровни и личная деталь после коммита наград |
| Гараж | [GARAGE.md](GARAGE.md) | Реализовано; `GET /garages/{player_id}` и три команды изменения |

Новые поля и сообщения добавлены совместимо с debug HTML-клиентом.
Проверка ID хоста — правило тестового потока, не полноценная авторизация.
Создание пилота переиспользует существующее создание двух сборок, каталог
и сохранение в БД; не заводим второй путь выдачи деталей для Unity.

`action_result` нужен и для отказов до вызова боевого обработчика
(чужой актор, матч уже завершён и т.п.). Он снимает ожидание конкретной
команды; обработку `state_update` не блокируем ожиданием ответа.
Ошибки формата команды также возвращаем отправителю понятным ответом.

`match_result` включает ID матча, победителя, награду XP, уровень до/после
и личную деталь либо null. Источник — существующий расчёт/запись наград,
без повторного ролла. Связь ID матча с `GameState` добавляем явно.
Результат отправляется только своему пилоту. Гараж после матча всё равно
перечитываем: он остаётся источником постоянного состояния.

## 4. Небольшая структура клиента

- `App`: запуск, выбранный пилот, адрес сервера, переходы экранов.
- `Networking`: HTTP-вызовы, один сокет на присоединённое лобби, JSON DTO.
- `Screens`: контроллеры логина, списка/комнаты лобби, гаража, результата;
  UXML/USS и общие карточки/стили.
- `Battle`: отображение карты/акторов, выделение клетки/оружия, HUD,
  отправка действия. Серверное состояние отделено от объектов сцены.
- `Editor`: небольшой скрипт первоначальной сборки сцен/ресурсов и
  Windows-билда, если он действительно убирает ручные повторения.

Две сцены достаточно: меню с переключаемыми экранами и арена.
Один объект уровня приложения живёт между ними и владеет соединением;
сцена не пересоздаёт WebSocket при старте игры. Подписки экрана снимаются
при его закрытии, чтобы не накапливать обработчики.

Колбэки сети передаются в главный поток Unity через простую очередь.
При смене пилота/выходе отменяем незавершённые запросы; ответы старого
пилота не могут обновить экран нового. Никаких DI-контейнеров, ECS,
универсального event bus и Unity Netcode: сервер уже говорит на REST/WS.

Сокет принимает текущие сообщения `lobby_state`, `state_update`,
`game_event` и новые адресные ответы. Полный снапшот применяем целиком,
объекты сцены связываем по `actor_id`. `version` не считаем уникальным
номером каждого кадра: сервер шлёт промежуточные состояния движения
до повышения версии. Не выбрасываем сообщения только из-за равной версии;
сначала сохраняем порядок получения на одном сокете.

## 5. Порядок реализации и критерии готовности

### Этап 0 — проект и связь

- [ ] Создать проект, закрепить редактор/пакеты, настроить Git и русские шрифты.
  Unity 6000.6.4f1 / URP 17.6.0; `Bootstrap` создана через Unity Pipeline.
  Проверка читаемости русских шрифтов и Git-настроек клиента ещё нужна.
- [ ] Пустое меню и лёгкая сцена арены; настройка адреса и понятные ошибки сети.
  Меню — UI Toolkit, адрес по умолчанию `127.0.0.1:8000`, ошибки REST выводятся
  на экран. Арена пока не создана.
- [ ] Проверить REST, JSON и WebSocket в Editor и Windows-сборке.

Готово: сборка запускается отдельно от редактора, читает список пилотов,
получает `lobby_state` из тестового лобби и не зависает при недоступном сервере.

### Этап 1 — выбор пилота и гараж

- [x] Создание профиля до лобби, выбор существующего и смена пилота.
  Экран загружает `GET /pilots`, создаёт профиль через `POST /pilots`, хранит
  последний UUID локально и получает `GET /garages/{player_id}` после выбора.
  В Editor проверены 58 существующих пилотов, выбор с загрузкой гаража и
  создание нового пилота с двумя сборками; ошибок в консоли не было.
- [x] Гараж: две сборки, оружие, статы, склад, навыки и редактирование.
  Реализован отдельный экран UI Toolkit; его постоянное описание и контракт
  находятся в [GARAGE.md](GARAGE.md).
- [x] Пустые/ошибочные состояния и сохранение последнего выбранного ID.
  Последний UUID сохраняется, но при запуске клиент намеренно остаётся на
  экране выбора пилота и открывает гараж только после явного выбора.

Готово: новый или выбранный пилот сразу видит свой гараж. Экран проверен в
Editor на реальном профиле с двумя сборками; возврат к пилотам и обновление
данных работают.

### Этап 2 — лобби

- [ ] Список, создание, PvP/бот, присоединение, команды и комната ожидания.
- [ ] Серверный состав с именами, выход до старта, проверка старта хостом.
- [ ] Автоматический переход обоих клиентов при старте по одному сокету.

Готово: один клиент начинает матч с ботом; два клиента входят разными
пилотами в одно PvP-лобби. Выход до старта действительно освобождает место.

### Этап 3 — первый управляемый матч

- [ ] Карта, простые мехи, камера, карточки, HUD и журнал событий.
- [ ] `MOVE`, `ATTACK`, `OVERWATCH`, `END_TURN`; адресные ответы команд.
- [ ] Владение акторами, очередь двух мехов, видимость и фаза нейтрального ИИ.

Готово: игрок делает все четыре действия против бота, ход возвращается
второму своему меху; неверная команда не оставляет UI заблокированным.
Первый практический рубеж — уже можно играть из Unity, даже без красивых моделей.

### Этап 4 — результат и связь с гаражом

- [ ] Структурированный результат после сохранения наград.
- [ ] Обновление реализованного гаража после пост-матчевых наград: новая
  деталь на складе и доступный выбор навыка после получения уровня.
- [ ] Обновление гаража, выход к лобби и создание следующего матча.

Готово: законченный матч меняет профиль в PostgreSQL; установленная деталь,
тюнинг и навык применяются к двум новым боевым акторам следующего матча.
После перезапуска клиента изменения остаются. Это завершённый первый прототип.

### Этап 5 — читаемость и проверка ноутбука

- [ ] Удобные размеры текста/кнопок, ясное выделение цели и активного меха.
- [ ] Короткая анимация движения, простые эффекты атаки и уничтожения;
  визуальные очереди не блокируют применение серверных данных.
- [ ] Измерение FPS/памяти и облегчение реальных узких мест в Windows-сборке.
- [ ] Краткая инструкция запуска клиента и сервера для следующего сеанса.

Готово: полный цикл понятен без debug HTML, интерфейс читается на экране
ноутбука, сборка работает с приемлемой скоростью. Детальный арт — следующий этап.

## 6. Проверка и распределение работы

Автоматически проверяем C#-компиляцию, разбор реальных HTTP/WS JSON,
вложенную карту, nullable `current_actor`, два собственных актора,
адресный отказ команды и применение последовательных снапшотов.
Изменения серверной проводки проверяем узкими HTTP/WS-тестами;
интеграционные проверки используют отдельную БД `_test`.

Практические сценарии: новый/существующий пилот, матч с ботом до результата,
два разных пилота в PvP, уничтоженная рука, исчезновение цели из видимости,
выход из комнаты, недоступный сервер и закрытие сокета.
При потере связи блокируем ввод, показываем причину и кнопку возврата.
Автоматический реконнект и восстановление после падения не блокируют прототип.

Для PvP используем две копии лёгкой сборки или Editor + сборку, а не два
редактора на ноутбуке. Проверку внешнего вида проводим в Game view и сборке;
batchmode подтверждает компиляцию/тесты, но не качество расположения UI.

Агент создаёт код, ресурсы UI, сцены/префабы, проверки и скрипт сборки.
Пользователь устанавливает и активирует редактор, запускает клиент для
визуальной оценки; замечания по управлению/виду задают следующую итерацию.
Проверка CLI/лицензии входит в этап 0; готовность редактора не предполагается
по одному наличию папки установки.

Документация Unity: [командная строка редактора](https://docs.unity3d.com/6000.0/Documentation/Manual/EditorCommandLineArguments.html),
[запуск тестов](https://docs.unity3d.com/Packages/com.unity.test-framework@1.4/manual/reference-command-line.html).

боевых правил, продажа/крафт/новые операции с оружием, финальные мех-модели,
сложные анимации и редактор карт в Unity.

Этап 1 и редактирование гаража завершены и вручную проверены в Editor.
Следующий шаг — лобби.
