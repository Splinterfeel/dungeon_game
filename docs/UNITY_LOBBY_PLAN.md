# Unity: список лобби и комната ожидания

Дата: 2026-10-06. Статус: экраны и сеть реализованы; основной smoke в Editor
пройден. Два отдельных клиента и полный рематч ещё не проверены.

Основа: готовые выбор пилота и гараж. После выбора сразу открывается лобби. План сверён с
`src/api/lobby.py`, `src/api/game.py`, `src/api/debug.py`, `src/lobby/lobby.py`
и DTO. Дамп/рестор исключены. Общий план — [UNITY_CLIENT_PLAN.md](UNITY_CLIENT_PLAN.md).

## 1. Состав интерфейса

### Список лобби

- Показать выбранного пилота; кнопки «Создать», «Обновить», «Присоединиться»,
  «Гараж», «Сменить пилота»; возврат из гаража ведёт в список лобби.
- Строка лобби: название, короткий ID (для одинаковых названий), режим,
  количество участников по командам, вместимость в пилотах, хост (короткий ID),
  состояние «Ожидание / Матч начат». Имена участников доступны только в комнате.
- Для целевого PvP — два пилота, каждый с двумя мехами. При создании фиксируем
  `players_num=2`; существующие лобби другой вместимости показываем с отметкой
  несовместимого формата и отключённым вступлением. Произвольное число пилотов
  сервер принимает, но оно не означает поддержку любого состава на фиксированной карте.
- Занятые и начатые комнаты показываем, но вступление нового участника отключаем.
  `game_started` означает наличие игры, включая завершённую; список не позволяет
  отличить идущий матч от завершённого. Не показывать выдуманный статус результата.
- Обновление при открытии, вручную и раз в 5 секунд только пока виден список.
  Один запрос одновременно; сохранять выделение по ID. При ошибке сохранять
  последний список с отметкой, что данные устарели; отдельное пустое состояние.

### Создание и присоединение

- Форма: название (пустое — сервер назначает его) и единственная галка
  «Против бота». Подпись: «Один пилот против бота, по два меха».
- Информация: карта `map_2`, два нейтральных врага в обоих режимах.
  Галок «Без нейтральных врагов», «Заполнить свободные места ботами» и выбора
  сборки бота нет: таких настроек сервер сейчас не предоставляет.
- PvP: выбор команды 1 или 2 с отображением занятости; для целевого 1v1
  предлагаем свободную. Бот: человек только в команде 1, команда 2 зарезервирована.
- Создание → сохранить полученный ID → обычный `connect_lobby` для хоста →
  открыть WS → дождаться состава комнаты. Создание само не занимает место.
- Если создание удалось, а вступление не удалось, сохранить ID и дать повторить
  вступление в ту же комнату; повторный клик не должен создавать новую.
- Вход использует выбранный UUID и существующий гараж. Не предлагать повторный
  выбор стартовых пресетов: `mech_presets` при существующем профиле игнорируются.
- Пока запрос выполняется, блокировать повторную отправку; обрабатывать
  HTTP-ошибки и ответы HTTP 200 с `result=false`, показывая `detail`.

### Комната ожидания

- Название/ID из выбранного лобби; серверный состав по двум командам:
  имя, отметки «Вы», «Хост», «Бот», число пилотов. У каждого пилота два меха.
  Не трактовать `connected_players` как список активных сетевых соединений.
- До старта бот ещё не входит в `participants`: показывать в команде 2
  информационный слот «Бот появится при старте», не поддельного участника.
- «Начать матч» только хосту: PvP — полный состав, бот — один человек команды 1;
  дополнительно требовать подключённый WS и полученный актуальный состав.
  Сервер остаётся окончательной проверкой. Свою команду после вступления не менять:
  для смены требуется выход и новое вступление.
- «Выйти из лобби» вызывает REST, затем закрывает WS и обновляет список.
  Для хоста подписать действие «Закрыть лобби»: его выход удаляет комнату,
  остальные получают `lobby_closed` и возвращаются в список с причиной.
- Пока пилот состоит в комнате, смена пилота и редактирование гаража недоступны.
  Настройка сборки — после выхода. Сервер собирает мехов из БД именно при старте;
  серверной блокировки редактирования гаража сейчас нет.
- Ready-галок, чата, приглашений, кика, передачи хоста, таймера и переключения
  режима после создания в текущем API нет.

## 2. Полное соответствие API

| Контракт | Использование |
| --- | --- |
| `GET /lobbies` | Список и актуализация занятости |
| `POST /lobbies` | Создание с именем, двумя местами, UUID хоста и `vs_bot` |
| `POST /connect_lobby` | Вступление выбранным пилотом и командой |
| `POST /leave_lobby` | Выход до старта, закрытие хостом |
| `POST /start_game` | Старт с `host_player_id`, обработка отказа |
| WS `/ws/{lobby_id}/{player_id}` | Один сокет комнаты и последующего матча |
| WS `lobby_state` | Состав, хост, режим, вместимость; статус выводим по данным |
| WS `lobby_closed` | Закрытие комнаты и очистка локального участия |
| WS `state_update` | Первый снимок боя и передача управления экрану матча |
| WS `game_event`, `action_result`, `match_result` | Не терять при переходе; обработка на этапе матча/результата |
| `POST /debug/rematch` | Кнопка хоста после завершения матча; новая игра тем же составом |
| `GET /mech_presets` | Не нужен экрану лобби: каталог стартовых пресетов, а не смена существующего гаража |

Рематч включён в покрытие, хотя endpoint debug: пользователь исключил только
дамп/рестор. Разместить его на экране результата, а не в комнате до старта.
Доступен хосту только после завершения; использует актуальные гаражи и тот же
сокет. После нового снимка сбросить результат предыдущего матча. В список/API
до старта кнопку рематча не переносить.

## 3. Сетевой жизненный цикл и ограничения

- После REST-вступления открыть WS; для подтверждения комнаты ждать
  `lobby_state`. REST-ответ старта сам по себе не является снимком матча.
- `lobby_state` со статусом старта может прийти раньше снимка: показать
  «Матч запускается». Переходить в матч один раз при первом `state_update`;
  такой снимок должен работать и без предшествующего `lobby_state` при реконнекте.
- Не закрывать сокет при смене экрана. Сообщения разбирать в порядке получения,
  доставлять в главный поток Unity; сохранять последний снимок и события перехода.
- Потеря WS блокирует старт/боевые команды. Кнопка «Подключиться повторно»
  открывает WS с теми же ID без повторного REST-вступления: участник уже записан.
  Автоматический реконнект для этого этапа необязателен.
- Разрыв WS и закрытие приложения не удаляют участника. Для возврата из
  не начатой комнаты обязательно `leave_lobby`; при недоступном сервере показать,
  что выход не подтверждён, сохранить контекст для повторной попытки.
- На время запросов выхода/старта учитывать гонки: пришедший снимок начавшегося
  боя отменяет локальное ожидание комнаты; отказ выхода после старта не очищает
  участие. Ответы старого экрана не должны менять новый экран/другого пилота.
- Отказ WS «лобби отсутствует / пилот не состоит» очищает локальный контекст.
  При перезапуске сервера лобби исчезают; восстановление комнаты не обещаем.
- Сервер не запрещает повторное участие UUID в других комнатах и не обеспечивает
  строгий 1v1 при REST-вступлении: клиент ограничивает свой поток одной комнатой
  и одной позицией на команду. Конкурентное вступление в одну команду может
  создать некорректный состав — при обнаружении выключить старт и предложить
  выйти/перевступить. Строгую валидацию команд/вступления после старта оформить
  отдельной серверной правкой, а не считать клиентскую блокировку защитой API.
- `lobby_state` не содержит признаков подключения участников, `game_started`
  и `ended`; текст `status` не использовать как единственный сигнал перехода.
  Участник без WS всё равно может учитываться сервером при старте.

## 4. Реализация по шагам

1. **Контракты и REST.** Добавить DTO лобби/запросов/ответов и методы в
   существующий `ServerApi`. Проверить реальные JSON, `result=false`, ошибки
   валидации, тайм-ауты. Расширить разбор ошибок для массивов `detail` FastAPI.
2. **Список и создание.** `LobbyListScreen`, UXML/USS в стиле готовых экранов;
   подключить переход из `PilotSelectionScreen`, обновление и выбор команды.
3. **WS и участие.** Один `LobbyConnection`, принадлежащий `ClientApp`,
   хранит ID комнаты/пилота, состояние соединения и полученные сообщения.
   Контекст участия хранить в том же `LobbyConnection`, без дублирования в
   `ClientSession` и без универсальной системы сетевых сервисов.
   Проверить `ClientWebSocket` в Editor и Windows-сборке.
4. **Комната.** `LobbyRoomScreen`, живой состав, правила кнопки старта,
   выход/закрытие, ручной реконнект и обработка гонок.
5. **Граница матча.** Передача сокета и первого снимка в `ScreenId.Battle`.
   Пока бой не реализован — минимальный экран «Матч начат» с диагностикой
   полученного снимка; не помечать этап управляемого матча выполненным.
6. **Рематч.** Методы/DTO включить сейчас; кнопку и полный сценарий завершить
   вместе с экраном результата. Если требуется принять весь scope сразу,
   завершить проверку рематча после реализации боя, не объявлять её пройденной заранее.
7. **Проверка и документация.** Проверить Editor + Windows-сборку с живым
   сервером, обновить этап 2 общего плана только по реально завершённым пунктам.

Открытый Editor понадобится для компиляции, Game View и сборки при реализации.
Для составления плана команды в Editor и изменение прав Pipeline не требуются.

## 5. Приёмка

- Пустой список, сервер недоступен, ручное/периодическое обновление;
  одинаковые названия и исчезнувшая выбранная комната.
- Создать PvP и комнату с ботом; пустое имя; только одно создание при двойном
  клике; восстановить вступление после успешного создания и сетевой ошибки.
- Два разных пилота (Editor + сборка): команды, имена, хост, полный состав;
  третий/повторный вход, занятая комната и начатый матч дают понятный результат.
- Не-хост не стартует; неполный состав не стартует; хост стартует; оба клиента
  получают первый снимок и переходят однократно. В боте виден резерв до старта,
  затем серверный участник и два его меха.
- Выход гостя освобождает место; выход хоста закрывает комнату у гостя;
  отказ/тайм-аут выхода не выдаётся за успешное освобождение места.
- Оборвать WS, подключиться повторно до и после старта; не отправлять повторный
  `connect_lobby`; проверить исчезновение комнаты после рестарта сервера.
- Проверить гонки старта/выхода, запоздалые ответы после навигации, закрытие
  приложения и отсутствие второго сокета/старых подписок.
- Настроенные ранее оба меха попадают в матч из гаража; UI не выдаёт новые пресеты.
- После готовности результата: рематч хостом, отказ гостю/до окончания,
  новый матч тем же составом и с актуальными сборками, без повторного результата.

Этап лобби принят, когда проходят сценарии списка, создания, участия, комнаты,
выхода, соединения и перехода в матч. Полное покрытие рематча принимается
отдельно на этапе результата. Дамп/рестор не реализуются.

## 6. Результат реализации 2026-10-06

- В сцену `Bootstrap` добавлен `LobbyScreen`; выбор/создание пилота открывает список.
  Используются новые `Lobby.uxml`/`Lobby.uss` в стиле существующих экранов.
- REST-команды в `ServerApi`, типизированные DTO в `Contracts/LobbyState.cs`.
  Ошибки HTTP и `result=false` отображаются отдельно от успешного выполнения;
  массивы ошибок валидации FastAPI поддерживаются.
- `LobbyConnection` принадлежит `ClientApp`: соединение, комната, последний
  снимок, результат и последние события. Сообщения применяются в главном потоке;
  очередь старого соединения отбрасывается при реконнекте. Клиент работает в фоне.
- Проверено в открытом Editor через Unity CLI: загрузка списка, создание,
  вступление, ручной реконнект, старт против бота и получение двух собственных
  мехов; PvP-состав с двумя именами, включение/выключение старта при входе/выходе
  гостя, выход хоста и получение закрытия вторым сокетом Unity.
- Windows x64 собран без ошибок и запущен без графики для проверки старта.
  Снимки Game View проверены; наложение формы исправлено разделением на колонки.
- Рематч подключён к API и кнопке результата, но полный матч и рематч ещё не
  прогонялись: управление боем — следующий этап. Два отдельных клиента,
  исчерпывающие гонки/сетевые отказы остаются в списке приёмки выше.
